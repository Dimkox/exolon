# Rollback plan — P1-11 release layer (один шаг, forward-fix)

Тип в `change-spec.yaml`: `strategy = forward_fix`, `maximum_steps = 1`. Конструкция.change
этому соответствует по построению: правки плоскотекстовые, ничего не генерируется, не мигрирует
и не сохраняется.

## Trigger conditions

- macOS-сборка показала неразвёрнутую подстановку (бандл печатает `$(MARKETING_VERSION)`) либо
  `version_single_source=MISMATCH` — то есть механизм подстановки в этой версии Xcode не применим.
- `xcodebuild -list`/`-showdestinations` не видит схему `Exolon`, либо archive падает **по причине
  «нет схемы»**, а не по подписи.
- Ревизия сломала что-то, кроме релизного слоя (в диффе должны быть только три путь-листа — см.
  `release.md` Go/no-go); либо владелец не принимает частичное закрытие P1-11 с отсрочкой hardening.

## Application rollback

Один шаг: `git revert <sha коммита этого change>`. Он чист, потому что:

- правка plist — две строки литерал → подстановка (реверт возвращает `0.3` / `1`);
- схема — **новый** файл, реверт его удаляет; `xcuserdata/…/xcschememanagement.plist` в коммит
  не попадает специально, чтобы реверт остался одношаговым;
- `project.pbxproj` не тронут ⇒ возвращать нечего;
- состояния нет: bundle id `com.exolon.remake` не менялся, значит `defaults` (HighScore, ключи
  `Exolon.Step10.*`) живы в обе стороны, LaunchServices перерегистрирует сборку без остатка.

Частичная forward-реcovery тоже одношаговая: `git checkout 403eb13 -- Exolon/Resources/Info.plist`
оставить схему (если подстановка не сработала, а схема нужна), либо удалить только
`Exolon.xcodeproj/xcshareddata` (если проблема в схеме).

## Data recovery / forward-fix

Данных нет — ни миграций, ни backfill, ни внешних записей. Известные асимметрии реверта надо
называть вслух, а не «чинить»:

- реверт plist **возвращает ложное** `0.3` — находка P1-11 по клаузе «версии» снова открыта;
- реверт схемы возвращает «общих схем нет» — v3-измеритель снова зеленеет, и это **не** признак
  здоровья: `v3_measurements.py` пинит `shared_xcschemes = 0` как состояние аудированного коммита,
  а не как желаемое. Владение cutover записано в `architecture.md`, удалять схему ради зелёного v3
  запрещено и красится `release_layer_check.py`.

## Verification after rollback

- `python3 evidence/release_layer_check.py --root .` → обязан стать **красным** (rc=1) ровно на
  отменённых клаузах; зелёный вердикт после реверта означал бы, что инструмент ничего не измеряет.
- `git diff --name-only 403eb13..HEAD` пуст по продукт-пути ⇒ дерево совпадает с базой маршрута.
- Датированные артефакты после любой ветки (rollback или forward-fix) остаются неизменными:
  `reports_blob_mismatches=0` обязан быть зелёным в обоих состояниях (AC-009).

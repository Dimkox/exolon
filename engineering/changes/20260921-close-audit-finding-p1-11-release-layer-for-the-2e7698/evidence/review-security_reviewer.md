## 1. Scope decision: is the hardened-runtime deferral honest?

**Judgement: honest, adequately recorded, and machine-guarded where it counts. It is not an under-scoped escape.** Reasons, each re-derived:

1. The technical premise is correct, not self-serving. Gatekeeper acceptance and notarization both require an Apple-issued Developer ID identity; `CODE_SIGN_IDENTITY = "-"` (ad-hoc, `Exolon.xcodeproj/project.pbxproj:1415,1434`), `CODE_SIGN_STYLE = Manual` (`:1416,1435`), `DEVELOPMENT_TEAM = ""` (`:1419,1438`) — grepped from the file, not restated from the brief. No value of `ENABLE_HARDENED_RUNTIME` makes an ad-hoc binary notarizable or Gatekeeper-accepted, so the flag cannot close any part of the P1-11 publishability clause it was asked to close.
2. The record does **not** claim the flag is security-irrelevant. `release.md:55-58` (§Deferred): `«…флаг не меняет исход Gatekeeper и недоступность нотаризации, **но включает рантайм-принуждение (library validation, запрет unsigned executable memory, ограничения отладки)** для бинарника, чья первая успешная сборка ещё не доказана»` (the key phrase is `release.md:57`). The real cost is named, and the deferral is argued on attribution grounds (do not mix the first-ever build proof with a runtime-enforcement change), which is a legitimate engineering reason.
3. It is gated, not silently dropped: `change-spec.yaml` `approvals.required_scopes` contains the named scope `defer_hardened_runtime`; `release.md:47-51` states the exact owner refusal path and the exact repair (`«ровно 2 таб-индентированные строки ENABLE_HARDENED_RUNTIME = YES; в **обоих** target-конфигах … и нужен отдельный macOS-прогон с codesign-флагом runtime»`); a concrete next-step verification command is recorded (`codesign -d --verbose=4 "$APP" 2>&1 | grep -o 'flags=0x[0-9a-f]*(.*)'` → token `runtime`, plus a negative control on the pre-fix build).
4. AC-007's guard works and is stronger than described. `release_layer_check.py:367` counts *key presence* per build-settings block (`sum(1 for g in objs if "ENABLE_HARDENED_RUNTIME" in bs(g))`), so it is value-agnostic. I proved this on a scratch clone: inserting `ENABLE_HARDENED_RUNTIME = NO;` into both target configs gives `hardened_runtime_key_count = 2  RED ожидалось 0` and `RESULT: NOT_READY (red_ac=1 …)`. An "explicitly hardening off" insertion therefore **cannot** masquerade as the recorded deferral.
5. The self-citation loophole is closed: `PLAN_FILES` (`release_layer_check.py:63`, exclusion rationale in the comment at `:59-62`) deliberately omits `evidence/` (where the verifier itself lives) and `brief.md` (auto-generated from the task wording and containing "hardened runtime"); control `deferral_record_ignores_brief_echo` passes (OK in my run).
6. The remaining honest weakness is drift, and it is NB-4 below: the guard pins the flag to *absent forever*, so it cannot be reused as the acceptance check of the future change that enables it.

The one fact the deferral leans on that I cannot check: that the binary has never compiled. `macos-validation-handout-v2.md:24` states `«** BUILD SUCCEEDED ** — первый в истории проекта type-check»`. `UNVERIFIABLE_ON_LINUX`; settled by `xcodebuild -project Exolon.xcodeproj -target Exolon -configuration Debug build` on macOS.

### NB-3 — `list_json_schemes=` is dead code whose emptiness is readable as a finding

`macos-probe.sh:73` greps the whitespace-stripped `xcodebuild -list -json` output for `'"scheme":\[[^]]*\]'`.

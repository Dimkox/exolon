## 1 — Surface-query API: edge cases

`TMXSurfaceQuery` (`TMXMapLoader.swift:124-239` at the 20:41 snapshot; `fallbackPlaneY` `:160`,
`surfaceTops` `:175`, `boundedSurfaceY` `:186`, `pistonGroundY` `:206`, `collisionRects` `:216`):
cell set built from the Collision layer with
`top = pixelHeight − row·tileHeight`, guarded by
`collision.gids.count == width·height` and `gid & 0x1FFF_FFFF != 0`.

Executed against the real product code (Linux build of the unmodified file **as of the 20:27
snapshot**, i.e. while `standingSurfaces` still existed — the API was rewritten at 20:37–20:41, see
the rule discussion below):

| case | construction | product result | judgment |
| --- | --- | --- | --- |
| no Collision layer | visual layer only | `cells=0 plane=96 spawnFeet=96 rects=0` | correct fail-safe to `defaultGroundY` |
| short/corrupt gid vector | `gids.count ≠ W·H` | identical to the above | guard works, no crash, no partial set |
| column with no solid cell | solids only at x=400 | foot span empty → plane fallback (`4` maps in the corpus: L01S17, L03S06, L04S09, L04S19) | correct, and the plane is a *global* min — the spawn may sit on an invisible floor far from any solid (shipped behaviour preserved) |
| y=0 floor | bottom row solid | `feet=16` (cell occupies [0,16]) | no off-by-one |
| top row | row 0 solid | `feet=384 = pixelHeight` | geometrically right, but the player's whole body lands **outside** the field; no corpus map hits it (max observed 272) — note only |
| two-tile-thick slab | rows 17+18 | candidates `[112]` only — the buried top is rejected | correct (`standingSurfaces` body-clear works) |
| low ceiling over the only floor | floor 96, slab [144,160] | floor rejected, spawn moved to 160 (on top of the slab) | conservative (never spawn inside solid) but it can hop a platform; none of the 125 maps hits it |
| Tiled flip flags | `gid = 0x8000_0001` | solid, `feet=96` | mask consistent with the deleted base renderer code |
| tie between two surfaces | — | comparator `a == b ? $0 < $1 : a < b` → prefers the **lower** top | deterministic, documented |
| straddled ledge | two tops in the 40 px foot span | nearest-to-marker wins | intended |

Consistency with runtime support (`Player.refreshGroundSupport`, `Player.swift:182-201`) is exact,
not approximate: the spawn foot span `centerX ∓ (46/2) ± 3` equals the Player's
`movementHitbox.minX+3 … maxX−3` (same `GameConstants.footSupportHorizontalInset`), and spawn
`centerY = feet + 32` with a 63 px movement box puts `box.minY` **exactly** on `feet`, inside the
1.5 px support tolerance. So no map spawns grounded and instantly falls. Verified for all 125 maps
(every chosen feet has a supporting cell in the inset span and is body-clear). Both halves of that
sentence were re-checked against the 20:38 rule: the support span still matches (the span arithmetic
did not change), but body-clearance no longer holds — see the 48/125 figure below.

0-based zone formula: `GameScene.zoneNumber(for:)` = `(stage−1)·25+(screen−1)` clamped 0…124
(`GameScene.swift:988-996`); stage starts `[0,25,50,75,100]` (`:642`) and stage-end bonus
`[24,49,74,99,124]` (`:620`) are the same numbering; the meter's `zone_index_formula` validates
`int(zoneNumber) == (stage−1)·25+(scene−1)` with the **file name** as the authority. Independently
re-measured: 125 files → zones 000…124, `zoneNumber` present on 117 (8 legacy L01S01…L01S08),
0 mismatches. **SOUND.**

Carried-Y on transition — the gap nobody in this package has recorded:
`GameScene.swift:638-646` uses `currentLevel.spawnCenter` **only** when `isStageStart`; otherwise
it keeps `spawnCenter.x` and takes `y = max(groundY + 32, carriedY)`. Wave B does not touch that
branch (correctly: `groundY` is byte-identical to the shipped `min(rect.maxY)` — see the real
measurement below), so the P1-2 fix is consumed by the runtime on **5 of 125 entries** — the

## 2 — SpriteKit-free path reuse

**SOUND, proven by execution.** `TMXMapLoader.swift:1-2` imports only `CoreGraphics` +
`Foundation`; no `SK*`/`SpriteKit`/`UIKit` token appears in it or in `GameConstants.swift` (only in
doc comments). `TMXSurfaceQuery`, `BeamFieldModel`, `TMXBeamGrouping` and
`resolvedPlayerBottom` all live in that file and this agent compiled the unmodified product file
(plus the harness's single `import FoundationXML` line) with `/opt/swift/usr/bin/swiftc` on Linux
against the 20260919 CoreGraphics shim and executed it over the whole corpus and 12 synthetic
grids — the same route `wave_b_harness/run.sh` uses, whose byte-delta check
(`ровно 1 строка импорта`) and negative control (`без стаба не собирается`) are both present in
`wave_b_harness/last-run.txt`. SpriteKit stayed where it belongs: `ForceFieldBarrier`
(`LevelObstacles.swift:768-790`) is the only SpriteKit type and it *delegates* to the SpriteKit-free
model. Caveat (style, not correctness): gameplay entity `BeamFieldModel` sits in a *map loader*
file — a Linux-harnessable `GamePlay/Beam*` file or a shared target would be the cleaner home;
splitting it now would fork the harness build, so accept and note as debt.
`TMXMapData.surfaceQuery` is a computed property, so every access rebuilds the cell set. At the
20:27 snapshot a level therefore built it twice (`TMXLevelRuntime.swift:63` and
`TMXTileMapRenderer.swift:17` via `map.surfaceQuery`); the writer fixed that at 20:38 by passing the
runtime's instance into the renderer (`TMXTileMapRenderer.swift:11 init(map:surfaceQuery:)`) — the
claim is now satisfied, but the meter's own source guard still greps the old expression and fails
(see the live-delta note below).

## 3 — Beam shared 25-HP pool

**SOUND** for the three asked properties, with the parallel audit's two caveats accepted as valid:

- *Destruction of the surviving side*: `isActive` is now computed from the pool
  (`LevelObstacles.swift:782`) so both sides die together; `field.onDestroy = { sides.forEach {
  $0.coverDestroyed() } }` (`TMXLevelRuntime.swift:439`) paints both covers black in one shot. A
  shot at an already-dead side cannot drain the pool twice: `registerHit()` guards on `isActive`
  and `destructionNotified` (`TMXMapLoader.swift:243-262`, `BeamFieldModel`), and
  `GameScene.swift:399` selects
  `first(where: { $0.isActive && … })`.
- *Hit attribution*: exactly one HP per bullet — `first(where:)` + `bullet.destroy()` + `continue`
  (`GameScene.swift:399-404`), so a thin bullet overlapping both halves of a pair drains 1, not 2,
  and the 1000-point award fires on the single destruction hit. Lethality to the player
  (`:569`) and the debug overlay (`:1099`) read the same `isActive` — no second source of truth.
  Grenades never touched beams before and still do not (unchanged behaviour).
- *Reload identity*: one `BeamFieldModel` per x-overlap **group** per **level instance**
  (`TMXLevelRuntime.swift:433-445`); `BeamFieldModel.sharedHitPoints` is an immutable `static let`,
  so there is no cross-level or global pool. Executed pool: destroys on hit 25, notifies once,
  `isActive` false after, extra hit returns false (`wave_b_swift.txt:2`).
- **MINOR, new (not in the parallel audit):** `field.onDestroy` captures the `sides` array
  strongly and every `ForceFieldBarrier` holds `field` strongly
  (`LevelObstacles.swift:771`) → a strong cycle that keeps each level's beam sides, fields and
  their `SKShapeNode`s alive after the level is replaced on transition. Small, but unbounded over a
  session and newly introduced by this design. Capture `[weak sides]` (or clear `onDestroy` after
  firing) and it disappears.
- `beamFields` (`TMXLevelRuntime.swift:35`, appended at `:444`) has no reader — identity is
  observable only through the sides. Either expose it (debug HUD "beam HP") or drop it.
- Grouping is x-interval overlap only, so two *different* beams stacked in one column would share a
  pool. Corpus: 20 markers / 10 maps / 10 fields, every group exactly 2 sides (re-measured
  independently ✓). Acceptable as a documented ruling; must stay an explicit ruling because the
  boxes are 272 px tall in a 384 px field.

## 4 — Bullet cull derivation

Constants: `GameConstants.swift:30-31` (`playerMinimumCenterX = 48/2 = 24`,
`playerMaximumCenterX = logicalSize.width + 32 = 544`), `:38` bullet 16×2,
`:42` `blasterCullMaximumX = playerMaximumCenterX + blasterBulletSize.width = 560`,
`:43` `blasterCullMinimumX = −16`. Consumer `BlasterBullet.swift:50-55` compares the named bounds.
`Player.swift:129` now clamps through the same two constants, so the pair cannot drift. No code
path still culls at 528: the surviving 528s are `LevelObstacles.swift:420` (bubble **spawn** x) and
`:850` (homing missile spawn) — positions, not culling (the parallel audit reached the same
conclusion). 560 also happens to be the corpus's rightmost Collision edge (re-measured: max solid
right edge 560, 61 maps solid right of 512, maps are 35×16 wide), so the reported dead corridor is
closed for shots in flight. **Design of the derivation is sound; the predicate is 2 px short of
its own stated goal** in two ways:

1. **Born-dead band.** `Player.blasterOrigin()` = `position.x ± 34`
   (`Player.swift:261-270`), so at the right clamp the shot spawns at x=578 > 560 and dies on its
   first `update`. The band is x ∈ (526, 544] (previously (494, 544]) — narrowed, not removed. The
   cull compares the bullet's **centre**; the defensible comparison for "entirely inside the
   reachable field" is the bullet's trailing edge against the player's rightmost *body* extent
   (`playerMaximumCenterX + playerSpriteSize.width/2 = 568`), i.e. centre > 576, or clamp the
   muzzle. AC-004's predicate (`cull ≥ clamp + bullet width`) passes today and still cannot see
   this hole.
2. **Neighbouring projectile not unified.** `Grenade.swift:80` culls at
   `logicalSize.width + 24` = 536 — the same class of corridor, still an inline literal, not
   derived from the clamp. Either route it through the same derived bound or record it as an
   accepted out-of-scope neighbour in `architecture.md` (the brief's ruling 3 argues from "no shot
   can disappear while it is still inside the reachable field", which the grenade violates).

## 5 — Piston lethality

**Anchor only.** Diffed against base `295690b`: the only changes in `PistonHazard`
(`LevelObstacles.swift:311-347`, class; init `:327-339`, hitbox `:341-347`) are literal →
named-constant hoists — `groundY − 64` →
`groundY − GameConstants.pistonTravel`, `CGSize(48,64)` → `pistonNodeSize`, hitbox
`+3 / width 42` → `pistonHitXInset / pistonHitWidth`. `hiddenY/exposedY/hitbox` arithmetic and the
phase machine are byte-identical, so no hitbox was widened to manufacture lethality. The single
gameplay input is `groundY`, now
`surfaceQuery.pistonGroundY(markerX:markerBottomY:)` (`TMXLevelRuntime.swift:294-300`,
`TMXMapLoader.swift:206-210`).

Independently re-measured with my own parser: 46 pistons / 27 maps ✓; anchor moved off the marker
row on 43 ✓; 3 use the fallback plane (L01S15 x128, L02S23/L05S23 x400 — markers at y=384 over
void shafts) ✓; new-anchor lethal 46/46 ✓; old-anchor lethal control **6/46** ✓ (this agent reached
6 independently, matching the writer's mid-audit correction of the merged probe's 3, and their
`tasks.md` deviation note explains the extra three as edge-grazes of the fallback plane); and —
the load-bearing one — the product's chosen anchor equals the **body-clear** floor on 46/46, so
the piston always emerges from a floor a standing player can actually occupy.

**MINOR — the foot band is not shared in product code.** `pistonGroundY` selects with
`groundY(atOrBelow: markerBottom + pistonTravel)` (max top under a limit), while spawn (20:38
snapshot) selects with `boundedSurfaceY` over `surfaceTops` — raw tops, no body-clear either. So
after the 20:41 rewrite **neither** consumer proves the surface it picked is one a standing body can
occupy; today the piston's choice happens to be body-clear on 46/46 (measured) and the spawn's does
not on 48/125. On future data an overhanging platform within 64 px above the marker row would
silently re-anchor a piston to a non-walkable surface, and the meter would not notice — its
`walkable_piston_surface` reference is python-only and hardcodes the body height as `63.0` instead
of resolving `playerStandingMovementSize.height` like every other number. Recommend one
body-clear candidate set in the query, used by both consumers (`≤ markerBottom + travel`, take the
max, else plane) and the piston's foot band taken from
`GameConstants.playerStandingMovementSize.height` in the meter. Ruling 4's "one definition of
ground at x" is then actually complete; today it is one *type* with two *selection rules*, and after
20:41 neither of them is the body-clear rule the parallel audit and I both measured against.

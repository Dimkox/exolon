Главное по бюджету:

1. **120 из 125 зон рисуются одним битмапом.** У 118 зон это `zone_NNN_original.png`
   (512×384) и у 2 — `zoneNNN_scenery.png`, то есть ровно один `SKSpriteNode`
   из `renderImageLayers()` (`TMXTileMapRenderer.swift:20-38`) вместо тайлов.
   Пять зон (`L01S01…S04`, `L01S07`) — единственные, где работает тайловый путь.
   Следовательно узловая стоимость типовой зоны — 15 узлов, и узлы **не** являются
   узким местом загрузки.
2. **98,4 % потенциальной VRAM — фоны**: 120 PNG размером 512×384 по 786 432 B
   RGBA = 94 371 840 B из 95 885 504 B. На зону это 45–60 % её резидентного
   отпечатка (медиана по зонам — **1 437 696 B ≈ 1,37 MiB**, min 561 152 B
   у `L01S02`, max 1 735 680 B у `L01S13`).
3. **Реальная горячая находка — не загрузка, а пересборка массивов в цикле**:
   `terrainRects` — вычисляемое свойство (`TMXLevelRuntime.swift:97`), которое
   заново аллоцирует весь список collision-прямоугольников при каждом обращении,
   а обращений за один фиксированный шаг бывает до **20**. По измеренным
   количествам это **до ~742 KiB/с** мусора на зоне `L03S20` и `L03S16`
   (детали и формула — в «Паттерны в цикле»).
4. Узловой потолок зоны, выводимый из данных (не из факта их заполнения):
   3 видимых слоя × 840 ячеек = 2 520 спрайтов + 1 битмап + 12 объектов.
   Фактический максимум — **263**, т.е. 10 % от структурного потолка; причина —
   пустые видимые слои (в `L01S05`/`L01S06` по 4 слоя, но 0 ненулевых ячеек).
5. Ни один ненулевой GID не был отброшен из-за ёмкости листа
   (`skipped_cells_no_texture = 0` на всех 125 картах) — то есть модель
   «тайл → спрайт» замкнута и считать узлы по данным корректно.

## Текстуры

* **Атласов нет.** `SKTextureAtlas` — 0 вхождений в код; `.xcassets`,
  `.atlas`, атласных `.plist` на диске нет. Все 153 PNG лежат в бандле
  отдельными ресурсами (см. также `assets-bundle.md` этой же папки).
* Мест вызова `SKTexture(imageNamed:)` — **23** (контроль C7): 2 в рендерере
  тайлов (`:25`, `:90`), 2 в рантайме зоны (`:421`, `:482`), 15 в
  `LevelObstacles.swift`, по 1 в `ExplosionEffect.swift:33`,
  `PlayerSpriteNode.swift:18`, `Grenade.swift:33`, `BlasterBullet.swift:21`.
* Разрешение имени файла → имени текстуры идёт через
  `URL(fileURLWithPath:).deletingPathExtension().lastPathComponent`
  (`:23-25`, `:85-87`), поэтому две ссылки `../images/tiles.gif` и
  `../images/rocks.gif` в `L01S04.tmx` по семантике кода разрешаются в
  `tiles`/`rocks` (PNG) — это наблюдение про путь резолва, а не оценка контента.
* Уникальных имён, которых касается загрузка текстур:
  * из TMX как тайл-листы — **3** имени на весь корпус (606 208 B RGBA);
  * как фоны `imagelayer` — 120 имён (94 371 840 B RGBA);
  * из TMX + объектов на одну зону — median **7**, max 11;
  * объединяемое множество за упорядоченный проход `L01S01…L05S25` — **141**
    имя, 95 575 040 B RGBA (91,1 MiB).
* Постоянный «сценовый» набор вне карт (`vitorc` 135 168 + `bubble` 73 728 +
  `circular_explosion` 40 960 + `missile` 8 192 + `blaster_explosion` 5 120 +
  `grenade`/`double_launcher_bullet`/`blaster_bullet`/`turret_bullet`) =
  **265 408 B** RGBA.
* Кэш листов `sheetTextures` — словарь **на экземпляр рендерера**, то есть на
  зону (`TMXTileMapRenderer.swift:11`); подтекстуры тайлов не кэшируются по
  `localIndex` вовсе. Вывод из этого (без измерения): на смену зоны
  `TMXTileMapRenderer` заново оборачивает те же самые листы, и за проход по
  125 зонам будет создано ≥781 подтекстуры тайлов плюс ~1 384 подтекстуры
  объектов (37 турелей × 8, 70 порталов × 8, 22 инкубатора × 8 яиц × 3 кадра).
* Что это значит для VRAM/draw call — честно: **я не измерял** ни residency, ни
  отсоединение текстур после `removeFromParent`. Арифметика даёт только верхнюю
  границу: если в моменте резидентны все текстуры зоны + сценовый набор, это
  ~1,4–1,7 MiB на зону и ≤1,9 MiB пика; если кэш SpriteKit держит всё, что
  когда-либо грузилось за 125 зон, верхняя граница — 91,4 MiB RGBA (×179 к байтам
  на диске). `ignoresSiblingOrder = true` (`AppDelegate.swift:22`) открывает
  переупорядочивание батчей, а ≤11 различных листов на зону означают, что
  теоретический потолок draw call мал, — но ни одно из этих двух утверждений
  нельзя считать фактом без `showsDrawCount`/`showsNodeCount` и Metal Frame
  Capture (см. чеклист).

## Паттерны в цикле

Всё перечисленное видно в коде статически; количества взяты из замеров карт.

1. **`terrainRects` пересобирается при каждом обращении**
   (`TMXLevelRuntime.swift:97-122`): копируется `mapRenderer.collisionRects`,
   затем для каждой зоны с исключениями идёт `rects.flatMap { subtract(...) }`
   (`:109`, `:118`), где `subtract` (`:447-480`) возвращает новый `[CGRect]`
   (до 4 кусков) на каждый прямоугольник. Обращения:
   `GameScene.swift:271` (через `solidRects`, каждый фикс. шаг),
   `:415` (на каждую пулю игрока), `:469` (на гранату), `:503` (на каждый
   вражеский снаряд), `:1081` (кадр отладки), `TMXLevelRuntime.swift:125`
   (внутри `solidRects`) и **`:159` — на каждое яйцо в цикле по яйцам**.
   Оценка по измеренным количествам (48 B на `CGRect`, вызовов на шаг =
   1 `solidRects` + 2 пули + N снарядов + 1 граната + 8·инкубаторов яиц):
   `L03S20` 12 вызовов × 1 056 B = **12 672 B/шаг ≈ 742 KiB/с**;
   `L03S16` 20 вызовов × 624 B ≈ 731 KiB/с; медиана по корпусу — 5,7 вызова/шаг.
   Это и есть главный кандидат в горячий путь, а не загрузка карты.
2. **Зоны с пересчётом вычитания каждый кадр:** 5 зон с триггером
   `changing_room`/`capsule` (`L01S10`, `L02S10`, `L03S11`, `L04S16`,
   `L05S10`) — исключение применяется безусловно; 13 зон с `blk_beacon_base` +
   `blk_control_beacon` — `flatMap`-ветка включается после уничтожения вышки.
3. **`updateDebugOverlay()` вызывает `debugOverlay.removeAllChildren()`
   безусловно каждый кадр** (`GameScene.swift:1075-1077`), а при включённом F1
   строит `SKShapeNode` + `CGPath` на каждый `terrainRects`-прямоугольник и на
   каждый хитбокс (`:1079-1128`) = **600–2 100 узлов/с** при R = 10…35.
4. **Строки в кадре:** `hud.update(state:)` вызывается из `update(_:)`
   (`:139`), а не из фикс. шага: 4 × `String(format:)` + 1 `String(...)` за кадр
   (`HUDNode.swift:57-62`) = 300 форматирований/с при 60 к/с, даже когда значения
   не меняются. `updateDebugText()` (`:140, 1062-1073`) добавляет массив
   `[String]`, `joined(separator:)` и конкатенацию — ещё ~5 строк/кадр.
   `bannerLabel`/`stepLabel` форматируются по событию — это нормально.
5. **Пересборки массивов по событию и по шагу:** `bullets/grenades/enemyBullets`
   через `.filter` (`:421, 475, 516`), `bubbles/eggs/homingMissiles` через
   `.filter` (`TMXLevelRuntime.swift:153, 161, 181`), `explosions`/
   `grenadeTrailDots` через ручной `var active: [...]` (`:1039-1055`) — по одному
   новому массиву на объект на шаг.
6. **Текстуры на событие, а не на тип:** `ExplosionEffect.init`
   (`ExplosionEffect.swift:14-50`) на каждый взрыв делает `SKTexture(imageNamed:)`
   + 5 или 10 новых

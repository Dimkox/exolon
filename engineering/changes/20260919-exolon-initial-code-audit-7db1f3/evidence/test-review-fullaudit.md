## 3. Обязательная правка №1: §9 не покрывает остаточный риск собственного понижения C1

- Понижение P0 → P3 обосновано таблицей из 5 будок (`architect:117-121`): у `L01S10` запас **16 px**, у `L02S10`/`L03S11`/`L04S16`/`L05S10` — **0 px** («впритык»).
- §9.2 в чеклист берёт **только** `L01S10`, то есть единственную будку, где ошибка на 1 px безвредна по построению. Нулевой запас — это случай, где «пол цел» держится ровно на точном совпадении границ, и именно он не отдан ни одной проверке.
- Первичный §11 отсылкой (§9.10) тоже не спасает: §11.1 — только зона 009, §11.3 — зон 034/060/090/109 не содержит (проверено чтением §11.2–11.3).
- Маппинг зон по формуле продукта `GameScene.swift:997` (`(stage-1)*25 + (screen-1)`): `L02S10`→**034**, `L03S11`→**060**, `L04S16`→**090**, `L05S10`→**109**.

**Требуемое изменение (копируемый пункт):** в §9 добавить `2б. Зоны 034 (L02S10), 060 (L03S11), 090 (L04S16), 109 (L05S10): кабина с нулевым зазором. Встать на верхнюю клетку пола, один UP → ON, второй UP → OFF; убедиться, что верхняя клетка пола не «лысая» (иначе P3 превращается в P1: exclusion `minY-16` срежет клетку, на которой стоишь).`

Второй, более мелкий, дефект того же пункта: §9.2 формулировкой «проверить **только** штатный флоу» сужает первичный §11.1, из которого выпадают п.6 (второй UP → OFF) и п.7 (поршни `x=64/192, y=320` при ON не убивают, при OFF убивают). Смысл кабинного toggle'а — именно lethality поршней; без п.7 проверка «кабина работоспособна» не подтверждает ничего, кроме того, что текст поменял цвет. ## 5. Обязательная правка №2: durability и «воспроизводимость» доказательств

1. **§10 утверждает «замеры синтеза … воспроизводятся командой из текста».** Для сканов `docs_researcher` это так (в evidence 7 inline-heredoc'ов `$ python3 - <<'PY'`). Для замеров архитектора (будки, beam-матрица, B-01-разбивка, контроль `off=32/48`) в evidence есть **только вывод**, команд нет; скрипты — в `/tmp/docsaudit/*` и `/tmp/*`, которые (а) эфемерны и (б) на этом хосте `/tmp` — 3 900+ записей от трёх недель разных прогонов, то есть через неделю их уже не отличить. §9.3 к тому же прямо отсылates к `/tmp/b01_measured.json` как к списку зон для человека на macOS — этот список до macOS не доедет.
2. Отчёт сам же это и зафиксировал (§6: «доказательства нигде, кроме рабочего дерева», нет `.gitignore`) — но не сделал из этого вывода для **собственного** артефакта. Правка: положить в `evidence/` три маленьких скрипта замера (будки/beam/B-01) и сам `b01_measured.json` (2.8 KB), а в §10 заменить «командой из текста» на конкретные пути. Тогда §10 перестаёт быть утверждением, которое ревьюер должен перепроверять против меня (п.1 моей таблицы).
3. **`requirements.md`: AC-F-007 оставлен `[ ]`**, хотя `grok_verify --mode pr` на финальном дереве **выполнен и пройден** (квитанция 01:18, `tree_fingerprint c91fa5bd…`, отчёт 01:10 входит в перечень 50 файлов квитанции). Это расхождение бумаг с фактом в сторону *недо-отчёта* — безопасно, но закрывать надо (AC-F-008 закрывается этой волной ревью).
4. Повторюсь про то, чего отчёт **не** делает хорошо: он не публикует скрипты замеров и одновременно объявляет себя «единственным авторитетом». Это единственное место, где «доказательность» утверждения слабее, чем заявлено в §10.

## 9. Вердикт по тест-гейпу: не-наличие XCTest — блокер или честно отслеживаемый бэклог? (п.5 брифа)

**Не блокер для этого деливерабла. Обоснование по пунктам:**

1. **Маршрут не имел права порождать XCTest.** `active-route.json`: `intent=review`, `write_agent=null`, `allowed_agents` — три аналитика и два ревьюера, `quality_profiles: ["base"]`, `human_gates: []`. Деливерабл — отчёт + доказательная база, а не поведение игры. Требовать тест на поведение там, где по контракту маршрута поведение не менялось (и `git diff 403eb13 b8aee42 -- Exolon` пуст, что я проверил), — значит требовать нарушения frozen-пути продукта. AC-008/AC-F-009 («product bytes remain unmodified») прямо запрещают обратное.
2. **В этой среде XCTest физически недостижим.** Для него нужны `xcodebuild` + Apple SDK + macOS/Simulator; на этом хосте нет ни Xcode, ни macOS, ни shared `.xcscheme` (§6, T2). Добавление XCTest-таргета ещё и потребовало бы правки `Exolon.xcodeproj/project.pbxproj`, то есть ровно того продукта, который маршрут заморозил. Ставить «блокируем аудит, потому что нет Swift-тестов» — значит блокировать единственную работу, которую этот маршрут мог сделать.
3. **Отчёт не превращает отсутствие тестов в ничего не значащий факт.** Он (а) считает его честно: `0 файлов` в §6 и в позиции бэклога T3; (б) фиксирует следствие: весь продуктовый вердикт остаётся статическим и передаётся человеку в §9; (в) выносит **упреждающее требование**: §7 P3 «C1-demoted (4 кабины с 0-px запасом — добавить константу и юнит-гейт при первом же Swift-таргете)», то есть гейт привязан к моменту, когда он станет технически возможен, а не «когда-нибудь».
4. **Что было бы блокером** (и чего нет): выдача parse-ONLY за валидацию; вывод P0-опровержения без противного контроля; «тесты factory PASS» как аргумент за продукт; ссылки на несуществующие артефакты. Первые три отсутствуют (см. §8 и пере-прогоны §1); четвёртое частично есть, но в виде *пути в /tmp* (§5) — то есть это дефект сохраняемости, а не мистификация: файл существует сейчас и я его прочитал.
5. **Что при этом остаётся настоящей (не блокирующей, но задокументированной) дырой покрытия:** весь продуктовый поведенческий слой — 0 автоматических characterization-тестов на коллизии, exclusion-формулу, `fallbackGroundY`, scoring-цикл и persistence. Отчёт это и не скрывает: §1.2 («потолок»), §6 («XCTest у игры: 0 файлов»), §7 (T3), §9 (10 ручных пунктов). Единственное, чего я потребовал бы сверх сказанного: **провести в §10 грань «это воспроизводимо только на Linux-хосте, а это проверит только человек на macOS»** — сейчас она читается по §9, но отдельным предложением не сформулирована.

**Итог:** бэклог-позиция T3 + требование юнит-гейта + §9-чеклист = корректная и достаточная для review-маршрута работа с гейпом. Блокировать деливерабл из-за отсутствия XCTest на Linux было бы методологической ошибкой, эквивалентной объявлению `parse` за `build`.
